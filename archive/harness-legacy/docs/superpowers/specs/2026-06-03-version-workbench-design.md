# Version Workbench Design

## 目标

在现有导入中心链路上补一个真实业务页，统一展示主数据、人员排班、需求预测、登录/状态日志这四类业务版本的当前状态。

第一阶段只做只读版本台账，不做新写入能力，不新增后端接口，不改变现有批次详情、结果追踪、对比结果和复核案例的业务边界。

## 背景

当前项目已经形成一条接近闭环的导入中心链路：

- CSV 上传
- 字段映射模板
- 批次记录
- 失败行修正
- 单批次应用入口
- 应用后结果卡片
- 已应用批次到版本结果上下文的定位
- 在版本结果语境里受控发起一次本地比对
- comparison run / review case 的只读查询和钻取

现在仍然缺一层跨批次、跨数据域的统一版本视图。用户能在单个批次详情页看结果，但很难快速回答这些问题：

- 当前四类业务数据各自最新版本是什么
- 这些版本分别来自哪个导入批次
- 应用时间是什么时候
- 当前是否有阻塞或信息缺失
- 下游已经形成了多少对比结果和复核案例
- 下一步应该进入哪个真实页面继续处理

## 方案选择

### 方案 A：继续只靠批次详情页串联

优点：

- 不新增页面
- 实现最快

缺点：

- 用户需要逐个批次点开
- 无法跨数据域统一扫描版本状态
- 难以成为后续生产流的稳定入口

### 方案 B：在导入中心下增加只读版本台账页

优点：

- 和现有导入、应用、结果追踪链路天然衔接
- 可以先做只读聚合，不扩大风险
- 后续可逐步承接更多版本管理动作

缺点：

- 需要补一个新的业务页和导航入口
- 需要在前端聚合现有多个查询结果

### 方案 C：直接做完整版本中心

优点：

- 名义上更完整
- 后续可扩展空间大

缺点：

- 容易立刻把发布、冻结、变更、审批一起带进来
- 超出当前 ready queue 清空后的最小重建原则

推荐并采用方案 B。

## 页面归属与路由

版本工作台不应作为新首页，也不应先挂到“计划与排班”。

它的正确归属是现有导入中心 / 数据质量链路下的并列业务页，因为：

- 上游是导入批次应用
- 下游是 comparison run、review case、结果追踪
- 页面同时覆盖主数据、排班、预测、日志四类版本，而不是单一业务域

建议路由：

- `/data-quality`：批次列表
- `/data-quality/[batchId]`：批次详情
- `/data-quality/versions`：版本工作台
- `/data-quality/comparison-runs/[runId]`
- `/data-quality/review-cases/[caseId]`

## 第一阶段范围

### 包含

- 新增只读版本工作台页 `/data-quality/versions`
- 展示四类业务版本的统一台账
- 每行至少展示：
  - 数据域
  - 当前版本号
  - 来源批次
  - 应用时间
  - 当前状态/阻塞口径
  - 下游影响摘要
  - 下一步入口
- 从版本工作台进入现有真实页面：
  - 批次详情
  - 结果追踪
  - comparison run
  - review case workspace

### 不包含

- 新依赖
- 新后端 API
- schema / migration
- 真实外部集成
- 权限
- 审批
- 导出
- 批量操作
- 发布 / 冻结 / 变更写入
- 自动排班
- 结算规则

## 用户角色

### 导入管理员

快速确认各数据域当前版本是否已经形成、来自哪个批次，以及是否存在阻塞或缺失。

### 运营 / 复核负责人

快速判断某个业务版本是否已经进入下游比对和复核链路，以及下一步应进入哪个页面继续处理。

## 页面结构

第一阶段不做卡片化首页，而做一张以扫描效率优先的版本台账。

### 顶部区域

- 页面标题：业务版本工作台
- 说明文案：只读查看当前业务版本、来源批次、阻塞状态和下游影响
- 轻量筛选：
  - 业务日
  - 数据域
  - 状态

### 主表格

每一行对应一个“当前业务版本上下文”。

建议列：

1. 数据域
2. 当前版本
3. 来源批次
4. 应用时间
5. 当前状态
6. 阻塞/缺失摘要
7. 下游影响
8. 操作

### 行内操作

只允许跳转到现有真实页面，不新增写入按钮。

建议操作优先级：

- 查看批次详情
- 查看结果追踪
- 查看对应对比运行
- 查看复核工作台

## 数据组织口径

第一阶段的“当前版本”定义不追求完整生产语义，而采用现有本地系统能稳定支撑的只读口径：

- 主数据：当前已应用主数据版本
- 人员排班：当前已应用排班版本
- 需求预测：当前已应用预测版本
- 登录/状态日志：当前已应用日志版本

如果某一数据域当前没有明确版本，页面要显式展示：

- 未生成
- 来源缺失
- 下游未定位

而不是假装有可用入口。

## 状态定义

第一阶段建议只做前端展示状态，不引入新的生产状态码。

### ready

- 已有明确业务版本
- 已有来源批次
- 可以进入批次详情或结果追踪

### blocked

- 版本未生成
- 来源批次缺失
- 下游结果语境不完整

### empty

- 当前数据域还没有版本记录

这些状态只服务于版本工作台第一页展示，不替代后端实体状态。

## 与现有页面的关系

### 批次详情页

仍然是单批次处理中心。

版本工作台不是替代它，而是为用户提供“先找版本，再进入具体批次”的入口。

### 结果追踪页

仍然负责单批次应用后的下游证据链。

版本工作台只显示摘要和入口，不在第一页复制结果追踪的大量明细。

### comparison run / review case

版本工作台不承载详情，只做是否存在、数量多少、入口在哪的摘要。

## 风险与边界

### 口径误导风险

如果把“当前版本”讲得过重，容易让用户误以为已经进入完整生产版本管理。

因此第一页必须明确：

- 这是导入中心下的版本台账
- 只基于当前本地已应用链路聚合
- 不承担完整发布/冻结/审批语义

### 范围膨胀风险

版本工作台很容易被继续要求加入：

- 直接发起计算
- 直接关闭复核
- 发布冻结
- 导出
- 权限

这些都不应进入第一阶段。

## 验收

- 版本工作台归属明确在 `data-quality`
- 不新增首页
- 第一阶段只做只读台账页
- 下一步任务拆分以 `R787 / US707-709 / IM087-089` 为起点
- 进入实现前，先把首个最小切片放入 `docs/current/**`
