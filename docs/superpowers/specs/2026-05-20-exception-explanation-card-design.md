# 履约异常解释卡 V1 设计

## 背景

履约日历已经能从团队周视图下钻到小组、成员、个人单日三轨详情。当前主管能看到缺口和异常，但还缺少一层业务解释：异常到底来自排班、登录还是状态，影响哪个时段，以及现场主管应先怎么判断。

本设计选择方案 A：在个人单日三轨详情页内联展示异常解释卡。这样先补齐最深层解释能力，不新增工作台，不新增左侧入口，也不把处理流做成审批或项目管理页面。

## 目标

- 让主管从小组矩阵点击异常后，进入个人单日详情即可看到异常解释。
- 每条异常必须落到员工、日期、时段和轨道。
- 异常解释只辅助现场判断，不承担正式审批、提交处理或权限流程。

## 页面位置

现有页面：`/person-timeline/[employeeId]?date=YYYY-MM-DD&team=...&group=...`

新增展示位置：

```txt
个人单日概览
三轨时间轴：排班 / 登录 / 状态
异常解释卡列表
```

异常解释卡不作为新页面，不增加侧边栏入口，不改变当前履约日历层级。

## 异常解释卡字段

每条卡片包含：

- 员工：员工编号和姓名，继承当前个人页上下文。
- 日期：继承当前个人页日期。
- 异常类型：登录缺口、状态不一致、登录不足等。
- 时间段：开始时间和结束时间。
- 涉及轨道：排班、登录、状态中的两条或三条。
- 影响时长：按小时展示，例如 `0.5h`。
- 证据说明：用业务语言解释轨道差异。
- 建议主管动作：例如联系员工确认漏登、现场确认状态原因。
- 优先级：高、中、低。

## 交互

- 小组成员单日矩阵中的异常标记继续进入个人单日详情。
- 个人单日详情展示三轨时间轴后，展示该员工当天全部异常解释卡。
- 第一版不做滚动定位锚点；如 URL 带异常标识，后续可再定位到具体卡片。
- 第一版不提供处理按钮、提交按钮、审批按钮或批量操作。

## 数据口径

第一版仍基于本地履约日历模型推导：

- 排班轨道存在但登录轨道缺失，形成登录缺口。
- 排班和登录存在但状态轨道为离线或不符合在线要求，形成状态不一致。
- 异常说明来自三轨对比，不写成开发验收列表。

## 不做范围

- 不做审批。
- 不做处理提交。
- 不做权限。
- 不做数据库。
- 不做真实外部接口。
- 不做导出。
- 不做批量操作。
- 不做自动排班。
- 不新增左侧入口。
- 不新增内部项目管理页面。
- 不在产品 UI 展示 PRD、Gate、Story、验收清单、待实现、暂不实现等内部过程词。

## 拆分建议

### R227 / US239 / F178

异常解释数据结构：个人单日详情需要暴露异常解释列表，每条异常落到员工、日期、时间段、轨道、影响时长和优先级。

### R228 / US240 / F179

个人单日异常解释卡：个人单日三轨详情下方展示异常解释卡，用业务语言说明证据和主管建议动作。

### R229 / US241 / F180

小组矩阵异常入口衔接：小组成员单日矩阵的异常标记进入个人单日详情后，个人页能展示对应日期的异常解释列表。

## 验收口径

- 主管从个人单日详情能看出异常来自排班、登录还是状态。
- 每条异常有明确时间段、影响时长、证据说明和建议主管动作。
- 小组成员单日矩阵仍能进入个人单日详情，并看到同一天异常解释。
- 产品 UI 不出现内部过程词。
- 不新增页面路由、不新增左侧入口、不新增依赖、不改后端、数据库、真实接口、权限、审批、导出、批量、自动排班或生产公式。
