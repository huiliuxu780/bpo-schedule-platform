# 班务变更申请月班表调整承接 v1.0

## 结论

IM308 要把 `班务变更申请` 里 `同意 -> 月班表调整 -> 保存调整 -> 已调整 -> 下一条` 做成排班师可连续处理的同页三栏闭环。页面主对象仍是一条班务变更申请；中间区域负责定位并调整当前申请对应的正式班表格子。

## 已确认产品决策

- 页面形态：同页三栏承接。
- 左栏：申请队列，默认服务连续处理。
- 中栏：月班表调整区，定位当前申请对应员工和日期格。
- 右栏：申请详情、处理说明、保存动作和轻量影响提示。
- 调整方式：当前格快速调整，只修改当前申请对应员工/日期格。
- `调整为`：固定班次下拉，使用现有班次代码，例如 `休息 / A5 / B2 / T1`。
- 保存前：显示轻量影响提示。
- 保存后：当前申请进入 `已调整`，列表回到申请队列并选中下一条待处理申请。

## 本轮做什么

- 把 `/roster-change-governance?month=2026-08` 从右侧抽屉调整承接改成同页三栏工作流。
- 选中申请后，在中栏展示该申请对应的正式班表格子。
- 点 `同意` 后进入当前格调整状态。
- 排班师从固定班次下拉选择目标班次。
- 显示轻量影响提示：
  - 当前班次来自正式班表。
  - 本次只调整当前员工/日期格。
  - 保存后会生成或关联班表修订结果。
- 保存调整时优先复用现有本地 roster revision/publish/request resolve API，形成真实 `已调整` 结果锚点。
- 保存成功后，当前申请显示 `已调整`，并自动选中下一条待处理申请。

## 本轮不做什么

- 不做换班双人联动。
- 不做完整工时、技能、覆盖、标准人力或预测校验。
- 不做完整月班表编辑器。
- 不做审批、权限、通知、导出、批量、自动排班。
- 不新增外部集成、Excel 导入、生产公式、结算或计费规则。
- 不新增数据库表、迁移或生产持久化字段；如果现有 API 无法支持真实修订锚点，实施时必须停下来重新确认 Gate。

## 状态规则

```txt
待处理申请
  - 同意 -> 当前格调整状态
  - 拒绝 -> 已处理 / 已拒绝
  - 跟进 -> 跟进中

当前格调整状态
  - 选择目标班次 -> 更新轻量影响提示
  - 保存调整 -> 已处理 / 已调整 / 关联修订锚点
  - 返回申请 -> 回到申请详情

保存成功
  - 当前申请离开待处理
  - 已处理列表显示 已调整
  - 队列自动选中下一条待处理申请
```

## 数据与接口边界

优先复用现有本地 API：

- `GET /api/v1/roster-requests`
- `GET /api/v1/roster-drafts/current-published`
- `POST /api/v1/roster-drafts/revisions/create`
- `POST /api/v1/roster-drafts/publish`
- `POST /api/v1/roster-requests/{request_id}/follow-up`
- `POST /api/v1/roster-requests/{request_id}/resolve`
- `POST /api/v1/roster-requests/{request_id}/close`

实施时的成功标准不是只改前端标签，而是保存调整后能读回：

- 申请状态为 `resolved`。
- `result_type` 为 `adjusted`。
- `linked_revision_version_id` 有值。
- 页面显示 `已调整` 和调整后的班表结果。

## 验收标准

- 打开 `/roster-change-governance?month=2026-08`，页面呈现同页三栏，不再把月班表调整塞进右侧抽屉。
- 待处理申请被选中后，中栏定位到对应员工/日期格。
- 点 `同意` 后可在中栏选择 `调整为` 班次。
- 保存前显示轻量影响提示。
- 保存调整后，该申请进入 `已调整`，并保留 revision 锚点。
- 保存后队列自动选中下一条待处理申请。
- 页面不出现 `班表变更中心`、版本时间线、source-cell diff、长结果标签或工程 ID 作为主对象。
- 本轮不出现审批、权限、通知、导出、批量、自动排班、预测、标准人力、Excel、生产公式、结算或计费规则。

## 下一步 Gate 建议

IM308 使用 `frontend-scaffold` Gate，原则上不新增后端迁移或后端持久化字段。允许修改现有 `班务变更申请` 前端、必要的前端测试、Harness 当前层和追踪文档。若实现发现现有 revision/publish/resolve API 无法完成真实修订锚点，必须停止并升级为新的 backend/database Gate。
