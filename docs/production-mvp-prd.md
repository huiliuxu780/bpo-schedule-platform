# 生产雏形大 PRD

## 1. 背景与目标

当前项目已经具备本地演示版能力：可以在本地 seed/process-memory 数据上展示 BPO WFM dashboard、需求计划、排班计划、0.5h 时段详情、风险、班次、不可用、供应商/组织和部分导入预览能力。它适合演示业务链路和页面方向，但还不能被理解为生产能力。

生产雏形的目标，是把本地演示版升级为一套可被业务方验收、可被后续拆分开发、可支撑真实数据闭环的产品定义。本文只定义需求，不实现功能，不拆用户故事，不修改 current queue。

生产雏形不是完整生产上线版。第一阶段先解决“数据能进来、主数据能对齐、排班和预测能查看、实际登录/状态能对比、异常能定位”的闭环；数据库、权限、审批、导出、批量、生产规则、结算和收费因子可以被描述为后续生产化能力，但不在本次文档整理动作中实现。

## 2. 当前本地演示版与生产雏形差距

| 领域 | 当前本地演示版 | 生产雏形要求 |
| --- | --- | --- |
| 排班粒度 | 已有排班计划汇总和 0.5h 时段详情 | 同时支持 0.5h 时段汇总和人员级排班明细，并能互相追溯 |
| 需求预测 | 有需求计划展示和本地数据 | 支持独立需求预测导入，按日期、职场、项目、时段、技能组、等级对齐 |
| 实际登录/状态 | 有本机导入预览和状态展示方向 | 能将登录日志、状态日志切分到时段，并与人员排班对比 |
| 主数据 | 有组织、人员、供应商展示方向 | 需要坐席、职场、供应商、项目、技能、绑定关系和状态管理口径 |
| 数据来源 | 本地 seed/process-memory 和本地 CSV 演示 | 需要明确上传/导入文件、批次、主键、校验、错误处理和版本 |
| 异常处理 | 有风险/异常展示和 drilldown | 需要异常类型、识别规则、复核结果、归因和处理闭环 |
| 生产能力 | 无数据库、无权限、无审批、无导出、无真实集成 | 可作为后续能力规划，但必须与第一阶段范围分开 |

## 3. 角色与使用场景

### 3.1 排班运营

排班运营负责导入或维护人员级排班，查看时段汇总是否满足需求预测，并定位缺口、错排、漏排、跨职场绑定异常等问题。

### 3.2 现场主管

现场主管关注某职场、某项目、某班次当天是否有人、是否登录、是否处于有效产能状态，以及人员实际状态与计划排班是否一致。

### 3.3 供应商负责人

供应商负责人关注本供应商人员排班、出勤、登录状态、异常原因和复核结果。第一阶段只定义数据和查看口径，不实现供应商权限隔离。

### 3.4 数据管理员

数据管理员负责上传/导入主数据、需求预测、排班、登录日志和状态日志，处理导入失败行、重复主键、缺失绑定、无效时间段等数据质量问题。

### 3.5 PM / 管理层

PM 和管理层关注整体供需差异、异常分布、供应商/职场/项目维度趋势，以及哪些能力仍停留在本地演示版或待开发状态。

## 4. 生产雏形业务主线

生产雏形的业务主线固定为：

```txt
主数据导入
  -> 需求预测导入
  -> 人员级排班导入或维护
  -> 0.5h 时段排班汇总生成
  -> 登录日志和状态日志导入
  -> 预测 / 排班 / 实际状态对比
  -> 异常识别
  -> 复核处理
```

这个主线必须同时回答三类问题：

- 需求预测要求某时段需要多少人。
- 排班计划在同一时段实际安排了多少人、具体是谁。
- 实际登录和状态证明这些人是否按计划到岗，并处于有效产能状态。

## 5. 第一阶段范围与非范围

### 5.1 第一阶段必须覆盖

- 上传或导入坐席、职场、供应商、项目、绑定关系、班次类型等主数据。
- 上传或导入人员级排班明细。
- 从人员级排班明细展开或汇总 0.5h 时段排班。
- 上传或导入独立需求预测数据。
- 上传或导入登录日志和状态日志。
- 按日期、职场、项目、时段、技能组、等级进行供需对比。
- 按员工查看计划排班轴与实际登录/状态轴。
- 识别预测缺口、排班缺口、未登录、迟到、早退、状态异常、主数据绑定缺失等异常。
- 记录每批导入结果、失败行、数据质量问题和复核结果。

### 5.2 第一阶段明确不实现

- 自动排班算法。
- 正式审批发布流。
- 导出能力。
- 批量调班或批量处理。
- 生产权限体系。
- 真实外部接口直连。
- 结算规则、收费因子和生产级公式。
- 完整考勤薪酬闭环。

### 5.3 可写入 PRD 但后续单独 Gate 的能力

- 数据库持久化和 schema。
- 用户、角色、权限边界。
- 审批、发布、冻结、解冻的正式流程。
- 报表导出和批量操作。
- 与 Excel、CORN、HR、WFM 或第三方系统的真实集成。
- 生产状态码、产能计算公式、结算规则、收费因子。

## 6. 上传/导入文件清单与导入规则

### 6.1 第一阶段上传/导入表

| 表 | 目的 | 粒度 | 第一阶段要求 |
| --- | --- | --- | --- |
| 坐席主数据 | 识别人员身份、供应商归属和有效状态 | 人员 | 必须支持导入 |
| 职场主数据 | 定义排班和登录发生地点 | 职场 | 必须支持导入 |
| 供应商主数据 | 定义人员供应方 | 供应商 | 必须支持导入 |
| 项目主数据 | 定义业务项目或队列 | 项目 | 必须支持导入 |
| 绑定关系 | 绑定员工、供应商、职场、项目、技能组 | 关系 | 必须支持导入 |
| 班次类型 | 定义班次名称、开始结束、休息/饭点规则 | 班次类型 | 必须支持导入或维护 |
| 人员级排班 | 定义每个员工每天的计划班次 | 员工 + 日期 + 班次 | 必须支持导入 |
| 需求预测 | 定义每个时段需要的人数 | 0.5h 时段 | 必须支持导入 |
| 登录日志 | 定义员工登录/登出事实 | 员工 + 时间点 | 必须支持导入 |
| 状态日志 | 定义员工状态区间 | 员工 + 时间区间 | 必须支持导入 |

### 6.2 导入批次规则

每次导入必须形成批次记录，至少包含：

- 批次 ID。
- 文件名。
- 文件类型。
- 上传人。
- 上传时间。
- 数据所属业务日期范围。
- 处理状态。
- 总行数、成功行数、失败行数、警告行数。
- 失败文件或失败行明细。
- 是否生成新版本。
- 是否参与当前对比计算。

### 6.3 导入处理规则

- 导入前必须预览字段映射和行数统计。
- 导入时必须校验必填字段、主键唯一性、时间格式、引用关系和状态字典。
- 重复主键必须有明确策略：拒绝、覆盖、生成新版本，不能静默合并。
- 导入失败不能阻断所有成功行，除非关键主数据或批次级规则失败。
- 导入结果必须可追溯到原始文件和批次。
- 第一阶段可以不实现回滚，但 PRD 必须保留回滚需求位置。

## 8. 主键与绑定关系

生产雏形必须在 PRD 层明确身份匹配规则，否则后续开发会在导入和对比阶段反复返工。

### 8.1 人员身份匹配

- 系统内部使用 `employee_id` 作为员工主键。
- 外部来源允许提供 `external_employee_id`，但必须通过坐席主数据映射到 `employee_id`。
- 同一个 `external_employee_id` 不能同时映射到多个有效员工。
- 同一个 `employee_id` 可以保留历史供应商或职场变更，但必须通过有效期区分。

### 8.2 业务维度绑定

- 排班、预测、登录和状态对比至少按 `business_date + workplace_id + project_id + interval` 对齐。
- 涉及人员级异常时，必须进一步按 `employee_id` 对齐。
- 涉及技能需求时，必须按 `skill_group + skill_level` 对齐。
- 主数据绑定缺失时，不能强行进入正常对比结果，应进入数据质量异常。

## 9. 时间规则

### 9.1 时段粒度

- 生产雏形固定使用 0.5h 作为时段汇总粒度。
- 人员级排班必须能展开为一个或多个 0.5h 时段。
- 需求预测必须能按 0.5h 时段提供预测人数。
- 登录和状态日志必须能切分到 0.5h 时段，用于与排班对比。

### 9.2 业务日和跨天

- `business_date` 是排班和预测对比的业务日期，不一定等同自然日。
- 跨天班次必须归属到一个明确业务日。
- 跨天登录和状态日志必须按业务日规则切分。
- 所有时间必须记录时区，职场默认时区来自职场主数据。

### 9.3 休息和饭点

- 休息和饭点是否计入已排人数，必须由班次类型或排班明细规则决定。
- 状态日志中的用餐、小休、培训、会议等状态是否计入有效产能，必须由状态字典决定。
- 对比时必须分别展示“已排人数”和“有效产能人数”，不能混为一个指标。

## 10. 状态字典

第一阶段必须至少定义状态字典口径：

| 状态 | 是否有效产能 | 说明 |
| --- | --- | --- |
| online | 是 | 在线工作 |
| offline | 否 | 离线或未登录 |
| break | 否 | 小休 |
| meal | 否 | 用餐 |
| training | 可配置 | 培训 |
| meeting | 可配置 | 会议 |
| unavailable | 否 | 不可用 |
| abnormal_absence | 否 | 异常离席 |
| unknown | 否 | 未识别状态，需要数据质量处理 |

状态字典要支持后续配置，但第一阶段可以先用固定字典做验收。

## 11. 需求、排班、实际状态的对比口径

### 11.1 需求预测 vs 0.5h 时段排班

目的：判断计划排班是否满足预测需求。

| 指标 | 公式口径 |
| --- | --- |
| forecast_agents | 预测人数 |
| scheduled_agents | 同时段已排人数 |
| schedule_gap | scheduled_agents - forecast_agents |
| coverage_rate | scheduled_agents / forecast_agents |

异常例子：

- 预测 20 人，已排 16 人，缺口 4 人。
- 预测 10 人，已排 15 人，超排 5 人。
- 某技能组预测存在，但排班没有任何匹配人员。

### 11.2 人员级排班 vs 实际登录

目的：判断员工是否按计划到岗。

异常例子：

- 计划 09:00 开始，员工 09:20 登录，标记迟到。
- 计划 18:00 结束，员工 17:30 登出，标记早退。
- 计划有班但无登录记录，标记未登录。
- 有登录但无有效排班，标记未排班登录。

### 11.3 人员级排班 vs 实际状态

目的：判断员工在排班时段内是否处于有效产能状态。

异常例子：

- 排班时段内状态为 `offline`。
- 排班时段内状态长期为 `break` 或 `meal`，超过规则阈值。
- 状态记录重叠或断档，进入数据质量异常。
- 员工登录存在，但状态全部为非有效产能。

## 12. 异常类型、识别规则与复核闭环

### 12.1 第一阶段异常类型

| 异常类型 | 来源 | 说明 |
| --- | --- | --- |
| forecast_shortage | 预测 vs 排班 | 预测人数大于已排人数 |
| forecast_overstaffed | 预测 vs 排班 | 已排人数明显大于预测人数 |
| missing_schedule_detail | 排班 | 时段汇总存在但无法追溯人员明细 |
| no_login | 排班 vs 登录 | 有排班但无登录 |
| late_login | 排班 vs 登录 | 登录晚于计划开始 |
| early_logout | 排班 vs 登录 | 登出早于计划结束 |
| unscheduled_login | 登录 vs 排班 | 有登录但无排班 |
| non_productive_status | 排班 vs 状态 | 排班时段内不是有效产能状态 |
| missing_master_data | 主数据 | 员工、职场、供应商、项目或技能绑定缺失 |
| invalid_time_range | 数据质量 | 开始结束时间非法、重叠或跨天规则缺失 |

### 12.2 复核结果

异常复核必须至少支持以下结果口径：

- 确认异常。
- 标记为正常。
- 补充原因。
- 归因到排班问题、人员问题、主数据问题、导入问题、预测问题或状态源问题。
- 记录复核人、复核时间和备注。

第一阶段可以只定义复核记录需求，不实现正式审批或权限。

| 差异对比 | 查看预测 vs 排班、排班 vs 登录、排班 vs 状态 |
| 异常中心 | 查看异常列表、异常详情、归因和复核结果 |
| 数据质量 | 查看导入失败、主键冲突、绑定缺失、时间非法、状态异常 |
| 经营总览 | 展示生产雏形汇总指标，但不得把本机演示数据误写成生产数据 |

## 14. 数据质量、版本、冻结与审计要求

### 14.1 数据质量规则

第一阶段至少识别：

- 必填字段为空。
- 员工主键重复。
- 外部员工 ID 无法映射。
- 员工无有效供应商、职场或项目绑定。
- 预测存在无效职场、项目、技能组或等级。
- 排班开始时间晚于结束时间。
- 排班跨天但无业务日规则。
- 登录无对应员工。
- 状态日志区间重叠或断档。
- 状态类型不在状态字典中。
- 时段汇总无法追溯到人员级明细。

### 14.2 版本规则

生产雏形至少需要以下版本概念：

- 主数据版本。
- 需求预测版本。
- 排班版本。
- 登录/状态导入批次。
- 异常识别批次。

对比结果必须能说明基于哪版预测、哪版排班、哪批登录/状态日志生成。

### 14.3 冻结与解冻

第一阶段可以先只定义冻结/解冻口径：

- 冻结后的主数据、预测版本、排班版本不得被静默覆盖。
- 解冻必须记录操作人、时间、原因。
- 冻结不等同审批，不代表正式发布流已经实现。

### 14.4 审计要求

第一阶段至少记录：

- 文件导入批次。
- 数据处理结果。
- 异常识别结果。
- 异常复核结果。
- 版本切换记录。
- 冻结/解冻记录。

## 18. 文档验收标准

本文后续拆分为 raw requirements、user stories 和开发批次前，必须能回答：

- 第一期到底上传哪些表。
- 哪些数据是汇总，哪些数据是人员级明细。
- 排班、需求、登录和状态如何对比。
- 坐席、职场、供应商、项目和绑定关系如何支撑业务。
- 哪些能力当前已经有本地演示，哪些明确待开发。
- 哪些生产能力暂缓，不能混入第一阶段实现。

验收时必须避免以下误解：

- 不把本地 seed/process-memory 能力写成生产持久化能力。
- 不把页面展示写成真实业务处理能力。
- 不把异常展示写成自动处置能力。
- 不把冻结口径写成正式审批发布流。
- 不把权限、导出、批量和真实集成混入第一阶段。
